Push. Build. Float.

Each git push becomes an immutable image. Traffic moves to it only after /healthz answers 200, and rollback points traffic back at the previous image.

What happens after you push

Four phases, always in this order. A failure in any one of them stops the deploy and leaves the running version untouched.

1 / build

Detects the runtime from your lockfile and builds one image.

The image is tagged with the commit hash and never modified afterwards, so v17 is byte-for-byte what it was last week.

2 / release

Runs the release command once, before any replica starts.

Put database migrations here. If it exits non-zero, nothing is swapped.

3 / health

Starts new replicas and polls the path you configured.

Traffic stays on the old version until every new replica returns a 2xx, or the timeout in shipyard.toml runs out.

4 / swap

Moves the router to the new replicas and keeps the old ones running.

shipyard rollback re-points the router at those warm replicas, so nothing has to rebuild.

One file, in the repo

Everything the phases above need is in shipyard.toml. Leave it out and Shipyard falls back to what it detected, as in the session at the top.

shipyard.tomlexample
# which port your app listens on
[app]
port = 3000

[release]
command = "npm run migrate"

[health]
path    = "/healthz"
timeout = "60s"

[scale]
replicas = 2

Your first deploy

Run these inside a git repo that already starts locally.

  1. Install the CLI and sign in.

    $ npm install -g shipyard-cli
$ shipyard login

  2. Create the app. This adds a shipyard git remote.

    $ shipyard create orders-api

  3. Push.

    $ git push shipyard main
